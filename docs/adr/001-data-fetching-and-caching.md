# ADR-001: Слой получения данных и кэширования

## Контекст

Требование: запросы к `/api/org-tree` должны проходить через слой кэширования
со `stale time` 5 секунд, избегать лишних запросов (stale-while-revalidate или
аналог), корректно отменяться при размонтировании компонента, а инвалидация
кэша должна происходить только при реальном изменении данных (актуально для
этапа 03 с live-обновлениями).

## Решение

Использовать `@tanstack/react-query` вместо самописного кэша на `useState`/`useRef`.

## Альтернативы

1. **Самописный хук** (`useEffect` + `Map`-кэш в модуле). Полный контроль,
   отсутствие зависимости, но: отмену запроса, гонки (race conditions) при
   быстром повторном монтировании, повторные подписки на один ключ и
   инвалидацию нужно реализовывать и тестировать вручную — риск багов,
   несоразмерный ценности «нет зависимости» в тестовом задании с дедлайном 2-3 дня.
2. **SWR** (vercel/swr). Похож по возможностям на react-query, но менее гибкий
   API для точечного обновления кэша (`setQueryData` с produce-функцией нужен
   в этапе 03 для live-патчей без рефетча).
3. **@tanstack/react-query** (выбрано). `staleTime` из коробки соответствует
   требованию «5 секунд»; `queryFn({ signal })` даёт отмену запроса без
   дополнительного кода; `queryClient.setQueryData` / `invalidateQueries`
   покрывают точечное обновление и целевую инвалидацию для этапа 03.

## Последствия

- Дополнительная зависимость в бандле (~13 КБ gzip) — учтено в бюджете
  «≤200 КБ gzip» для этапа 04.
- Кэш живёт в `QueryClient` вне React-дерева компонентов — упрощает точечные
  обновления из WebSocket-обработчика на этапе 03 (не нужен контекст/проп-дриллинг).
- Логика повторных запросов (`retry`), поведение при потере фокуса окна
  (`refetchOnWindowFocus: false` — намеренно отключено, т.к. echo-обновления
  приходят по WS/патчам, а не по рефокусу) конфигурируется в одном месте
  (`client/src/api/queryClient.ts`).
