# ADR-004: Режим просмотра (дерево/таблица) и модель сортировки

## Контекст

Задание допускает два равноценных варианта UI: переключатель «Дерево / Таблица»
ИЛИ split-view при ширине ≥1280px. Также задан специфичный жест сортировки:
обычный клик по заголовку сортирует, двойной клик — сортирует в обратном порядке.

## Решение

**Режим просмотра.** Не выбирать один из двух вариантов, а реализовать оба через
чистый CSS: `Panel` всегда в DOM, видимость управляется пропом `$visible`
(производным от состояния переключателя) на узких экранах, но с
`@media (min-width: 1280px) { display: block }`, которая перекрывает `$visible`
и показывает обе панели одновременно. Сам переключатель скрывается той же
медиа-запросью на ≥1280px, где он избыточен.

**Сортировка (пересмотрено после ручной проверки — см. «Обновление» ниже).**
Клик по заголовку переключает направление (`asc`/`desc`) для этого столбца;
при клике на другой столбец — сортирует по нему по возрастанию. Двойной клик
всегда выставляет убывание напрямую (не через тоггл), независимо от текущего
состояния.

## Альтернативы

1. **Только переключатель** (`useState<'tree'|'table'>`, без split-view).
   Проще, но не использует доступную ширину экрана на десктопе и не
   соответствует явно упомянутому в задании варианту split-view.
2. **Тоггл сортировки на одном клике** (клик — asc, повторный клик по тому же
   столбцу — desc, как в большинстве таблиц). Это стандартный паттерн, но
   задание прямо называет именно двойной клик триггером обратного порядка —
   реализация через одиночный повторный клик не соответствовала бы
   формулировке требования буквально.

## Последствия

- Оба режима (дерево и таблица) всегда смонтированы в DOM на ≥1280px —
  небольшой лишний рендер по сравнению с полностью условным рендерингом, но
  зато состояние (раскрытые узлы, скролл таблицы) не сбрасывается при ресайзе
  окна через порог 1280px.
- Двойной клик по заголовку не поддерживает «вернуть по возрастанию» одним
  дальнейшим двойным кликом (он снова даст `desc`) — для возврата к `asc`
  нужен одиночный клик.

## Обновление: реальный баг найден при ручной проверке пользователем

Первая версия («альтернатива 2» выше отклонена») делала одиночный клик
безусловным присвоением `asc`, а не тогглом. На практике это означало: если
столбец уже отсортирован по возрастанию, повторный одиночный клик по нему
ничего не меняет (`setSort({column, direction: "asc"})` с теми же
значениями) — визуально «клик не сработал». Пользователь, ожидающий
стандартного поведения таблиц (клик по тому же столбцу — тоггл направления),
кликал повторно несколько раз без видимого эффекта и только случайный
достаточно быстрый повторный клик (интерпретированный браузером как
`dblclick`) давал `desc` — отсюда репортнутое «иногда нужно трижды кликнуть».

Это не было гипотетическим — баг обнаружился по прямой жалобе пользователя
после реального использования приложения в браузере, не через тесты или
ревью кода (код «выглядел правильно» и полностью соответствовал тексту
задания). Исправление: клик по уже активному столбцу тоггловит `asc ↔ desc`;
клик по другому столбцу — `asc`. Двойной клик всё ещё надёжно даёт `desc`
для ЛЮБОГО столбца, потому что реальный двойной клик — это `click, click,
dblclick`: два клика подряд по одному столбцу нейтрализуют друг друга по
направлению (тоггл-тоггл), а `dblclick` затем принудительно ставит `desc`.

Отклонённая ранее «альтернатива 2» (тоггл на одиночном клике) была отклонена
из-за буквального соответствия формулировке задания «двойной клик —
обратная [сортировка]» — но, как показала реальная проверка, буквальное
соответствие произвело функционально худший UX. Пересмотрено в пользу
тоггла: он не противоречит формулировке (двойной клик всё ещё надёжно даёт
обратный порядок), но делает каждый одиночный клик видимо осмысленным.
