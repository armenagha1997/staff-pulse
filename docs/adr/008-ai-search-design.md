# ADR-008: Дизайн AI-поиска

## Контекст

Задание: «строка поиска принимает естественный язык; ответ —
структурированный фильтр на клиенте; fallback — текстовый поиск». Никаких
требований к конкретному провайдеру или к обязательному наличию API-ключа.
При этом `docker-compose up` должен работать «из коробки» у любого
проверяющего — без обязательного секрета.

## Решение

Трёхуровневая цепочка, всегда заканчивающаяся структурированным фильтром:

1. **LLM (опционально)** — если задан `ANTHROPIC_API_KEY`, сервер
   (`server/src/llmSearch.ts`) отправляет запрос в Claude с forced tool-use
   (`tool_choice: { type: "tool", name: "apply_org_filter" }`) — ответ
   МОДЕЛИ — это и есть структурированный фильтр, без парсинга свободного
   текста. Таймаут 5с; любая ошибка (нет ключа, сеть, таймаут, неожидан-
   ная форма ответа) → `null`, вызывающий код переходит к следующему уровню.
2. **Эвристика (офлайн, по умолчанию)** — `server/src/aiSearch.ts`,
   `heuristicParse`: регулярные выражения на ключевые слова уровня
   (дивизион/отдел/команда) и паттерны «эффективность выше/ниже N»,
   «бюджет больше/меньше N (млн/тыс)», «сотрудников больше/меньше N».
   Не находит ни одного паттерна → весь запрос становится `nameContains`.
   Работает без сети и без ключей — именно поэтому `docker-compose up`
   не требует `ANTHROPIC_API_KEY` для прохождения этой части задания.
3. **Текстовый fallback на клиенте** — если *весь* HTTP-раунд-трип к
   `/api/ai-search` не удался (сеть недоступна, не-2xx, невалидный JSON),
   `client/src/api/aiSearch.ts` формирует `{ nameContains: query }` локально.
   Это и есть буквально «fallback — текстовый поиск» из задания.

Результат в обоих случаях — один и тот же тип `StructuredFilter`, который
клиент применяет через чистую функцию `matchesFilter` (`lib/aiFilter.ts`,
покрыта unit-тестами) к уже посчитанным `aggregatedRows`.

**Применение фильтра — по-разному в дереве и в таблице.** Таблица
буквально скрывает несовпадающие строки (та же семантика, что у обычного
фильтра по имени из этапа 02). Дерево вместо скрытия **тускнеет**
(`opacity: 0.35`) для несовпадающих узлов, а предки совпадений
автоматически разворачиваются — скрыть несовпадающий узел в дереве было бы
неверно, если один из его потомков совпадает (иерархию нельзя разорвать).

## Найденный при живом тестировании баг

Регулярки эвристики изначально использовали `\w*` для суффиксов слов
(«эффективност\w*», «бюджет\w*», «сотрудник\w*»). `\w` в JavaScript матчит
только ASCII — реальные словоформы («эффективностью», «бюджетом»,
«сотрудников») не проходили, и структурированные паттерны тихо не
срабатывали, откатываясь к `nameContains` на весь запрос. Пойман не
ревью кода, а юнит-тестами (`server/src/aiSearch.test.ts`), которые
намеренно используют естественные словоформы, а не словарную форму — 5 из
7 тестов сразу упали. Исправление — `[а-яё]*` вместо `\w*`.

## Альтернативы

1. **Обязательный вызов LLM** (без офлайн-эвристики). Отклонено: сделало
   бы бонус-фичу нерабочей без секрета у проверяющего, противоречит
   принципу «`docker-compose up` работает из коробки».
2. **Только текстовый поиск** (без попытки структурного парсинга).
   Проще, но не решает буквальную формулировку задания («ответ —
   структурированный фильтр»).
3. **Один и тот же способ показа результатов в дереве и таблице**
   (например, скрытие в обоих). Отклонено из-за иерархии: скрытие узла в
   дереве без учёта того, что его потомок мог совпасть, дало бы неверный
   результат — потомок стал бы недостижим.

## Последствия

- `StructuredFilter` определён независимо на клиенте (zod-схема) и на
  сервере (TS interface) — та же модель дублирования, что и `OrgNode` между
  клиентом и сервером с самого этапа 01 (нет общего пакета типов в этом
  монорепозитории).
- LLM-путь никогда не тестировался с реальным ключом в этом окружении (нет
  доступа к секретам во время разработки) — корректность именно этой ветки
  проверена только вручную по контракту Anthropic Messages API/tool-use, не
  сквозным прогоном с реальным вызовом.
