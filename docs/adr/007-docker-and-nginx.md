# ADR-007: Docker Compose и Nginx

## Контекст

Задание требует: `docker-compose up` поднимает клиент и сервер, конфиг через
`.env`; Nginx проксирует API, отдаёт статику с gzip; production-сборка
≤200 КБ gzip.

## Решение

Два сервиса (`docker-compose.yml`, корень репозитория):

- **`server`** — multi-stage образ (`server/Dockerfile`): стадия `build`
  компилирует TypeScript (`tsc`), финальная стадия ставит только
  `--omit=dev` зависимости и копирует `dist/`. Слушает 4000 внутри сети
  Docker, порт не публикуется наружу (клиенту он не нужен — только Nginx).
- **`client`** — multi-stage: стадия `build` (Node) собирает Vite-продакшн-
  бандл, финальная стадия — `nginx:1.27-alpine`, копирующая `dist/` и
  `nginx.conf`. Публикует `${CLIENT_PORT:-8080}:80`.

`nginx.conf`: `gzip on` для `text/*`, JS, JSON, SVG; `location /api/` и
`location /ws` проксируют на `http://server:4000` (имя сервиса резолвится
через Docker-сеть compose); `/ws` дополнительно поднимает
`Upgrade`/`Connection` заголовки для WebSocket.

`.env` (см. `.env.example`) конфигурирует `CLIENT_PORT` (внешний порт) и
опционально `ANTHROPIC_API_KEY`/`ANTHROPIC_MODEL` для AI-поиска (см.
[ADR-008](008-ai-search-design.md)) — `docker-compose up` работает даже без
`.env` благодаря значениям по умолчанию (`${VAR:-default}` в
`docker-compose.yml`).

## Что пошло не так при первом прогоне (и как это нашлось)

Оба Dockerfile сначала использовали `node:20-alpine`. `docker compose build`
(реально запущенный, не просто написанный) падал на `npm install` с
`Cannot read properties of null (reading 'edgesOut')` — известный баг
арбориста в npm, поставляемом с этим тегом образа. Попытка исправить через
`npm install -g npm@latest` тоже не сработала: свежий npm (12.x) требует
Node ≥22/24, а базовый образ — Node 20. Решение — поднять сами базовые
образы до `node:22-alpine` (совпадает с версией Node, реально используемой
в этом проекте локально), без каких-либо доп. шагов обновления npm. Без
реального запуска `docker compose build` эта несовместимость осталась бы
незамеченной до первого запуска у проверяющего.

## Проверка (реально выполнена, не только написана)

`docker compose build && docker compose up -d`, затем: статика отдаётся
(`GET /` → 200), JS-бандл идёт с `Content-Encoding: gzip`, `/api/org-tree`
проксируется на сервер, WebSocket (`/ws`) успешно устанавливает соединение
и доставляет live-патчи через Nginx, `/api/ai-search` тоже проксируется
корректно, смена `CLIENT_PORT` в `.env` действительно меняет внешний порт.
Итоговый gzip-бандл — **~109 КБ**, в пределах бюджета 200 КБ.

## Альтернативы

1. **Один образ** (Node-сервер сам отдаёт статику + проксирует /API).
   Проще (один Dockerfile, один сервис), но не даёт продакшн-gzip/кэширование
   статики уровня Nginx и противоречит формулировке задания («Nginx:
   проксирует API, отдаёт статику»), которая явно предполагает Nginx как
   отдельный слой.
2. **Единый монорепо-контекст сборки** (Dockerfile в корне, копирующий и
   `client/`, и `server/`). Отклонено: раздельные контексты (`./client`,
   `./server`) позволяют пересобирать/деплоить сервисы независимо и не
   тащат в образ клиента серверный код и наоборот.

## Последствия

- Оба сервиса устанавливают зависимости «с нуля» в своём Docker-контексте
  (нет `package-lock.json` на уровне пакета — он есть только в корне
  монорепозитория для npm workspaces) — сборка воспроизводима по диапазонам
  версий в `package.json`, но не зафиксирована с точностью до патч-версии
  внутри контейнера. Для монорепозитория с Docker-контекстами на уровне
  пакета это осознанный трейд-офф простоты над строгой воспроизводимостью.
