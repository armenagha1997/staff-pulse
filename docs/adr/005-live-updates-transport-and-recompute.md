# ADR-005: Транспорт live-обновлений и инкрементальный пересчёт агрегатов

## Контекст

Задание требует: сервер транслирует изменения в реальном времени (клиент —
WebSocket/SSE/поллинг); клиент применяет патч без полного рефетча;
пересчёт агрегатов — только для затронутого узла и его предков; обновлённые
ячейки — fade-out ~1.5с; индикатор соединения с экспоненциальным backoff.

## Решение

**Транспорт: WebSocket** (`server/src/live.ts`, путь `/ws`, тот же HTTP-сервер).
Каждые 2–5с сервер случайно мутирует один узел (headcount/budget/performance)
и рассылает патч всем подключённым клиентам:
`{ type: "node-updated", id, changes: Partial<...> }`. Мутация происходит
независимо от того, есть ли подключённые клиенты — стор остаётся источником
истины, согласованным с тем, что вернёт `GET /api/org-tree` при рефетче.

**Инкрементальный пересчёт** (`client/src/lib/liveUpdate.ts`,
`client/src/lib/aggregate.ts`): вместо повторного вызова `aggregateTree`
(полный O(n) проход) на каждый патч:
1. Мутируем собственные поля затронутого узла напрямую (`Object.assign`, O(1)).
2. Идём по цепочке предков (`idChain`, есть только id, не поиск), у каждого
   пересчитываем rollup через `recomputeOwnRollup` — используя уже известные
   rollup'ы его детей из `aggById`, а не полный обход поддерева. Итог: O(глубина).
3. Клонируем только узлы на этом пути (`cloneAlongChain`), чтобы получить
   новый `tree`-массив (React должен увидеть новую ссылку) — необработанные
   ветки сохраняют исходную ссылку на объект (для потенциальной мемоизации).

Корректность (только затронутый узел + предки меняются, остальные — нет,
ссылки соседних поддеревьев не мутируются) покрыта тестами в
`liveUpdate.test.ts`.

**Индикатор соединения и backoff** (`client/src/api/liveSocket.ts`):
`connecting` → `open` → при разрыве `reconnecting` с экспоненциальной паузой
(`1000 * 2^attempt`, капа 30с, + случайный джиттер до 300мс, чтобы не все
клиенты переподключались синхронно).

**Fade-out**: `useFadingHighlights` добавляет id в набор «недавно обновлённых»
сразу, затем убирает его через ~60мс. CSS-переход задан асимметрично:
`transition: background-color ${updated ? '0s' : '1.5s'} ease-out` — включение
подсветки происходит мгновенно (0s), а возврат к обычному фону анимируется
1.5с. Симметричный переход (одна и та же длительность в обе стороны) был
первой попыткой и не сработал: подсветка сама начинала «наплывать» 1.5с и
успевала набрать лишь несколько процентов яркости за 60мс до того, как её
начинали гасить — эффект был почти незаметен. Это обнаружено не по коду, а по
реальному прогону в браузере (см. README, раздел AI) — скриншот показывает
чёткую вспышку у патченного узла и у его предка одновременно.

## Альтернативы

1. **SSE**. Проще (обычный HTTP, авто-переподключение браузером), но
   однонаправленный — для этой задачи достаточно, однако WebSocket явно
   упомянут первым в списке и не требует полифилла для будущей
   двунаправленной связи (например, ack от клиента).
2. **Поллинг** (даже «эффективный», с backoff). Требует явно управлять
   частотой и мёртвым временем; WebSocket даёт push без периодических
   пустых запросов при отсутствии изменений — прямее решает «минимизацию
   лишних запросов».
3. **Полный `aggregateTree` на каждый патч** вместо инкрементального
   пересчёта. При ~60 узлах разница в производительности неощутима, но это
   буквально не то, что требует формулировка задания («пересчёт только для
   затронутого узла и его предков») — и не масштабируется на реальный размер
   орг-структуры (тысячи узлов, патчи каждые доли секунды).

## Последствия

- `nodesById`/`aggById` в `useLiveOrgData` — мутируемые `ref`, не React state;
  единственный триггер ре-рендера — замена `tree`/`aggregatedRows` (новые
  верхнеуровневые ссылки). Это осознанное отступление от «всё через
  иммутабельный state» в пользу O(глубина) вместо O(n) на каждый патч.
- Патч на узел, ещё не попавший в `nodesById` (гонка между WS-подключением и
  начальной загрузкой данных), молча игнорируется (`applyLivePatch` вернёт
  `null`) — конечная согласованность обеспечивается следующим тиком.
