# Модель данных

## Контракт API

`GET /api/org-tree` возвращает плоский массив узлов:

```ts
interface OrgNode {
  id: string;
  name: string;
  parentId: string | null; // null у корневых узлов (дивизионов)
  headcount: number;       // собственная численность узла (без потомков)
  budget: number;          // собственный бюджет узла (без потомков), в рублях
  performance: number;     // 0..100
  updatedAt: string;       // ISO-8601
}
```

Валидируется на клиенте схемой `OrgNodeSchema` (zod), см. `client/src/api/schema.ts`.
Невалидная форма (лишнее/отсутствующее поле, `performance` вне `[0,100]` и т.п.) —
ошибка, а не молчаливое искажение данных.

## Дерево

Иерархия: **дивизион (уровень 1) → отдел (уровень 2) → команда (уровень 3)**.
Мок-данные — минимум 40 узлов (фактически ~55-60, т.к. количество отделов/команд
на узел рандомизировано в диапазоне), ровно 3 уровня.

`buildTree(nodes: OrgNode[])` (`client/src/lib/tree.ts`):
1. Строит `Map<id, TreeNode>`, где `TreeNode = OrgNode & { children: TreeNode[]; level: number }`.
2. Один проход по узлам: узел с `parentId`, найденным в `Map`, добавляется в
   `children` родителя; иначе — в список корней.
3. BFS/DFS-проход от корней проставляет `level`, начиная с 1.

Сложность: O(n) по числу узлов, без ограничения на глубину.

## Агрегация

Реализована в `client/src/lib/aggregate.ts` (`aggregateTree`), покрыта тестами
в `aggregate.test.ts`. Для каждого узла агрегат включает **сам узел + всех потомков**:

```
totalHeadcount(node) = node.headcount + Σ totalHeadcount(child)  для child ∈ node.children
totalBudget(node)    = node.budget    + Σ totalBudget(child)
avgPerformance(node) = Σ (n.performance * n.headcount) / Σ n.headcount
                        по node и всем потомкам n (взвешено по headcount)
```

Один проход снизу вверх (post-order DFS), O(n) по числу узлов, возвращает
плоский `AggregatedRow[]` — одна строка на каждый узел дерева (используется
напрямую как источник строк аналитической таблицы).

В `App.tsx` вызывается как `useMemo(() => aggregateTree(tree), [tree])`, где
`tree` — тоже мемоизированный результат `buildTree(nodes)`. Пересчёт происходит
только при изменении ссылки на `nodes` (т.е. при реальном получении новых
данных от API), а не при каждом рендере (переключение вида, сортировка,
фильтр, выбор строки — все эти состояния не входят в зависимости `useMemo`
и не вызывают повторный проход по дереву).

## Live-патчи

Сервер транслирует изменения по WebSocket (`/ws`, `server/src/live.ts`): раз в
2–5 секунд случайно мутирует headcount, budget или performance одного узла и
рассылает всем подключённым клиентам:

```ts
interface OrgNodePatch {
  type: "node-updated";
  id: string;                       // изменённый узел
  changes: Partial<Pick<OrgNode, "headcount" | "budget" | "performance" | "updatedAt">>;
}
```

Валидируется на клиенте той же схемой-подходом, что и основной ответ API
(`OrgNodePatchSchema`, zod) — невалидный фрейм молча отбрасывается, не ломая
соединение.

**Патчи не идут через react-query.** REST-кэш (`['org-tree']`) хранит только
исходный снимок с первой загрузки/рефетча — это структурная правда (какие
узлы существуют, кто чей родитель), которая не меняется живыми патчами.
Патчи применяются напрямую к отдельной мутируемой модели в
`useLiveOrgData` (`client/src/features/live/useLiveOrgData.ts`):

1. `nodesById`/`aggById` — `Map`, хранящиеся в `ref`, а не в React state;
   именно их мутирует `applyLivePatch` (`client/src/lib/liveUpdate.ts`).
2. Затронутый узел получает новые собственные поля (`Object.assign`, O(1)).
3. Пересчёт rollup идёт только по цепочке **этого узла и его предков**
   (`recomputeOwnRollup` использует уже готовые rollup'ы дочерних узлов, не
   пересчитывая их) — O(глубина), не O(n). См. [ADR-005](adr/005-live-updates-transport-and-recompute.md).
4. Только узлы на этой цепочке клонируются, чтобы дать React новую ссылку на
   `tree`; необработанные ветки сохраняют объектную идентичность.

Это даёт «применяет патч без полного рефетча» и «пересчёт только для
затронутого узла и его предков» буквально, а не только по духу.

**Fade-out.** Каждый id из цепочки «узел + предки» получает кратковременную
метку «обновлён» (`useFadingHighlights`, ~60мс), пока которая активна — стили
строки (дерево и таблица) переключаются на цвет подсветки БЕЗ анимации
(0s), а как только метка снимается — обычный фон возвращается с переходом
1.5с. Итог: мгновенная вспышка, затем плавное затухание ~1.5с (не наоборот).
